# GitHub State Mirror

## Project Overview

A Go service that mirrors GitHub state into SQLite, providing a fast local API surface. This is a **cache** — the SQLite DB is disposable and gets nuked+recreated when `schema.sql` changes.

## Architecture

- `internal/actor/` — Context-based principal-key propagation, display shortening, and verified display-name propagation. `WithName`/`NameFromContext` take only GitHub-verified answers: a user's login, an app's slug, an installation's account login. The package is stdlib-only, so anything may import it. A "principal" identifies WHO asks: `user:<id>`, `app:<id>`, `app-installation:<id>`, or a token fingerprint. It gates what the cache REVEALS, not what it STORES. The name is display-only and never a key.
- `internal/freshness/` — framework of the Generic cache freshness with zero GitHub knowledge. `Manager.Drain` waits out in-flight detached fetches at shutdown.
- `internal/database/` — SQLite schema + sqlc-generated queries (`dbgen/` is codegen, do not edit)
- `internal/ghdata/` — Domain store wrapping sqlc with transaction logic: global truth writes (`SyncOrgTruth`, `UpsertPRWithChecks`, ...), the show layer's `access_grants`/`deny_cache`, and the dashboard reads. The grant-writing paths (`SyncOrgTruth`, `RecordGrant`) opportunistically sweep expired grants and denials after committing. That sweep is `maybePruneAccessControl`: best-effort, log-on-error, and throttled to about one run per 10 min behind an atomic last-run stamp. Reads (`HasGrant`, `GrantsByPrincipal`, `CountLiveGrants`, `ListGrantPrincipals`) filter on expiry regardless.
- `internal/ghclient/` — client of the API of the GraphQL of the GitHub REST +. It holds the token→identity cache, `AppAuthenticator` (JWT, installation tokens, the App webhook-delivery log), and `doJSON`'s transient retries. It also holds the GraphQL fetch families. The rate and exchange observers live there too, and they put every call on the dashboard Timeline. docs/ghclient.md covers all of it. That includes why a 4xx is never retried, and why owner queries pin `ownerAffiliations: OWNER`.
- `internal/reqtimeline/` — in-memory ring of TIMED traffic events behind the dashboard's "Timeline" chart. **Everything the mirror exchanges is on the chart. A gap is a bug** (operator ruling: an earlier cut excluded background traffic and was reverted). The bounds are 24h and 100k events. Eviction is lazy, and lanes are bounded by construction. The ring resets on start. docs/dashboard/timeline-ring.md.
- `internal/ratemeter/` — Passive rate-limit observation, read by the dashboard's "Rate limit" tab. Every upstream path reports its `X-RateLimit-*` headers here, so a credential's standing costs no call of its own. The store is IN-MEMORY and resets on start. It is bounded, and dead observations age out lazily. docs/ratemeter.md — the window-aware death rule, the bounds, and every observation field.
- `internal/auth/` — GitHub OAuth login + signed-cookie sessions for the dashboard (no DB knowledge). Its client is built through `httpobs`. The two GitHub calls a sign-in makes are thus on the Timeline like everything else.
- `internal/httpobs/` — stdlib leaf that makes an outbound HTTP client report every request from its TRANSPORT. It is the choke point behind the no-invisible-requests rule below. auth, the passthrough proxy, and the API layer's own client all use it.
- `internal/sync/` — Bridge layer: the org list-sync fetcher, periodic refresh, webhook dispatch (always-apply), the global consistency checker, and the delivery-gap replayer (`replay.go`)
- `internal/webhook/` - parsing of the event of the + of the Webhook HTTP handler, and the `Queue` that applies deliveries. The handler answers GitHub once the delivery is in the journal (`queued`, or `duplicate` for a delivery id it already holds). One worker applies journaled deliveries in arrival order, and on start it applies whatever the last process left unapplied. After each apply it hands the outcome to any `IngestNotifier` (`internal/notify`), which is non-blocking by contract. An optional `DeliveryRecorder` times EVERY try onto the Timeline, a rejected one included. docs/webhooks/dispatch.md. This is the per-event matrix. docs/webhooks/delivery-recorder.md - the recorder-only dispositions.
- `internal/inbox/` - The webhook journal: its own SQLite file next to the cache DB, `synchronous(FULL)`, not rebuilt. A row is the raw delivery, keyed by `X-GitHub-Delivery`, kept 72h after it is applied so a redelivery is recognized.
- `internal/notify/` — Subscriber notifications, the "mirror-ingest webhooks". An authenticated client registers its own endpoint (`/_mirror/subscriptions`), and the mirror POSTs it an HMAC-signed notification after a delivery is applied. Consumers thus stop racing the mirror's ingestion with their own GitHub webhooks. docs/notifications.md — the config DB, the fail-closed gating, retries. This is the `/_mirror/*` namespace.
- `internal/api/` — chi router, REST handlers, GraphQL cache assembler, the **show layer** (`reveal.go`), and the GitHub passthrough proxy (`proxy.go`). It also holds the in-memory request-disposition log (`requestlog.go`, with per-route-shape grouping in `requestgroups.go`), the uncached-traffic SHAPE capture and implementation brief (`shapes.go` + `brief.go`), and the web dashboard (`dashboard.go` + embedded `web/`).
- `internal/api/web/` — Dashboard front-end. `src/*.ts` is the only source, compiled to the embedded, gitignored build output `assets/*.js`. CI builds it.
- `cmd/server/` — Entry point (drains in-flight fetches before closing the DB on shutdown)

## The global-truth model (operator directive, 2026-07-03)

> "just because nobody has fetched something doesn't mean we get to ignore updates from webhooks for it. there's only 1 cache because there's only 1 true state, the appropriate parts of the cache are revealed to users/apps based on their permission model (i.e. were they able to access this resource directly through github -> yes -> ok we can serve the cache for this resource to them)"

Storage and authorization are **separate axes**:

1. **ONE global truth store.** These tables carry NO actor column: `repos`, `pull_requests`, `pr_labels`, `commit_checks`, `workflow_runs`, `contents_cache`, `git_commits_cache`, `git_commit_miss_cache`, `pulls_list_cache`, `commits_list_cache`, `compare_cache`, `commit_ci_cache`, `workflow_runs_cache`, `pull_files_cache`, `closed_pull_cache`, `pull_diff406_cache`, `branches_list_cache`, `label_cache`. `readme_cache` and `workflows_cache` carry none either. There is one row per fact, because there is one true state. Webhooks and every principal's fetches all maintain the same rows. Caches stay per-credential. `install_token_cache` and `repo_installation_cache` key on the app principal. `installation_repos_cache`, `hooks_cache` and `owner_repos_cache` key on the BEARER's fingerprint. An owner's repo listing is what THAT token can see, so a shared row replays one credential's private repos to another. A minted token, an app's installation coverage, one token's repository view, and a repo's or org's webhook config are per-credential answers, not shared truth. Per-credential keying is self-gating, because a row is only ever replayed to the credential GitHub already answered. That property is what lets those routes skip the show layer. For the ADMIN-only hook listings it is also what keeps them SAFE. The show layer proves only READ access. A global row therefore leaks a repo's webhook endpoints to a read-only caller.
2. **Webhooks ALWAYS apply.** The dispatcher never asks "who has this cached?". A delivery for a repo nobody ever fetched upserts the `repos` row straight from the payload's own `repository` object (`absorbRepoFromPayload`), then applies. There is no `skipped` disposition, no on-demand pull, and no `ActorsForRepo` gate. Those were deleted.
3. **Reads show by permission** (`internal/api/reveal.go`). Serving a cached resource needs proof that the caller can read it from GitHub directly. Things count as proof. The repo is **public** in truth, which is the fast path and makes no GitHub call. The principal holds a live **access grant**. Or a live **probe** answers 2xx, which is `GET /repos/{owner}/{repo}` with the caller's own token. Grants are earned only from GitHub's own answers. An org list-sync **replace-syncs** the principal's grants to exactly the repos GitHub returned them (`source=list_sync`). A successful probe records one grant (`source=probe`). The grant TTL is about 24h (`ghdata.GrantTTL`). An authoritative denial (404, or a 403 that is not rate limiting) is cached in `deny_cache` for about 5m (`ghdata.DenyTTL`) and replayed without touching GitHub. A transient failure (5xx, 429, rate-limited 403, network) is NEVER cached and fails only that one request. Unknown visibility (`repos.visibility` = `''`) counts as private. Fail closed.

## Key Constraints

- **No migrations, and nothing to declare** — `schema.sql` is hashed with comments scrubbed and whitespace normalized (`internal/database/fingerprint.go`). A DB recording a different hash is nuked and recreated on open. Editing a table nukes. Editing a comment does not, and nothing else nukes at all. A data problem is Reconcile's job, not a nuke's. The number this replaced was hand-maintained, and a change that forgot it deployed against the table it no longer described. History: docs/schema-history.md
- **A new table goes in `schema_plain.sql`, with plain SQL in `internal/ghdata`** — a branch push may not change a generated `*.gen.go` file. CI's sqlc check fails when `schema.sql` or `queries/*.sql` drift from `dbgen/`. `schema_plain.sql` is outside sqlc and inside the schema: `db.go` creates and fingerprints it with `schema.sql`. Its queries run through `Store.dbx`, which binds the transaction the context carries.
- **sqlc codegen** — run `sqlc generate` after modifying `schema.sql` or `queries/*.sql`
- **Freshness/data separation** — `internal/freshness/` must never import GitHub-specific packages
- **One writer at a time, queued in-process, and never across a network call** — every write to a database opened. This is through `database.OpenDSN` passes its write gate (`internal/database/gate.go`). A transaction holds it from BeginTx to Commit or Rollback, an autocommit write for its own statement. Waiters are admitted oldest-first, so SQLite's sleeping busy-handler never runs. A transaction does DB reads and writes only. Read state, commit, make the slow call, then open a new transaction to write. The api, sync and notify test binaries run under `database.RunWithTxGuard`, which fails any test that sends a request from a goroutine holding the gate.
- **A webhook delivery is kept before GitHub is answered, and applied as one transaction** - `webhook.Handler` writes the delivery to the inbox and answers. GitHub never waits on an apply. `WebhookDispatcher.Dispatch` runs every write of one delivery inside `ghdata.Store.InTx`. Store methods read the transaction from the context (`database.InTx`, `qx(ctx)`). A store method's own transaction becomes a savepoint inside it. A write sent to the pool from inside that context fails with `database.ErrWriteOutsideTx` instead of waiting on its own lock. At shutdown the worker finishes the delivery in hand and the rest wait in the inbox.
- **The write lock is measured, not guessed** - `db.write_wait` is the queue for the gate and `db.write_hold` is one writer's hold, both on the Latency tab. A hold past 1s logs WARN with the releasing goroutine's stack, which names the holder.
- **Lazy fetches are detached, backoff-gated, and drained** — `freshness.Manager.doFetch` runs the fetch. Its metadata writes on a `context.WithoutCancel`-derived context, bounded only by `fetchSafetyTimeout` (5m). A client that aborts its request thus cannot kill the shared multi-page org-repos fetch mid-flight, nor stop the result being stored. A short caller deadline is deliberately NOT re-applied, because the old webhook-deadline re-application killed fetches half-done. Every detached fetch is tracked in an inflight WaitGroup. `Manager.Drain(timeout)` waits for them, and `cmd/server` calls it after `ListenAndServe` returns, BEFORE `db.Close()`. A fetch thus can never write to a closed DB at shutdown. An error-state row inside its `retry_after` window is NOT re-fetched by a lazy caller. `EnsureFreshOutcome` reports the stored error instead. A failing upstream is thus not hammered on every request. A deliberate refresh (a periodic trigger) bypasses the backoff. When `/graphql` serves the stale cache after a refresh failure it sets the `X-GSM-Stale: true` and `X-GSM-Last-Fetched` response headers, and WARN-logs with the principal. Headers only: the body stays identity-test-identical.
- **One global truth, revealed by permission (replaces per-actor isolation)** — the security boundary is the Show LAYER, not storage. Revealing `owner/repo` to a principal needs the repo to be public, a live grant, or a live probe with THAT principal's own token. Fail-closed rules must not regress. Unknown visibility counts as private. Only an authoritative denial is cached. Grants expire. A list-sync REPLACE-syncs. docs/reveal-layer.md — principal resolution, the App-identity path, and the background App credential.
- **APPLY THE PAYLOAD. INVALIDATION IS THE LAST RESORT.** This is the most-violated rule in this repo. Every violation looks the same. GitHub hands us the new value in the delivery. We THROW IT AWAY and delete a row.

  We then buy the same fact back with a second HTTP request we did not need. A webhook is not a cache-busting ping. It is the answer. **The procedure, for every handler and every cached route, in order.** First: does the payload carry the new value? WRITE IT.

  Second: does it carry enough to DERIVE it? Derive it and write that. Third, only if neither holds, you may invalidate. That covers an unparseable body, or a change whose result the payload genuinely does not state, such as a rename or a recomputed `mergeable`. Then say in a comment WHY the payload cannot answer. "Invalidate, the next reader will refetch" is a bug report, not a design.

  A push alone hands you `ref` and `after`, which is the branch's exact new tip. It also hands you `before`, `created`/`deleted`/`forced`, `base_ref`, `repository.default_branch`, and up to 2,048 full commit objects. See docs/webhooks/dispatch.md for the per-event matrix. The COALESCE rules that keep a webhook from blanking known state. This is the routes still violating this. Every surviving response-cache flush is inventoried in docs/webhooks/invalidations.md with a verdict: justified, or owed with the conversion named.

  The count can only go down, and a new flush belongs in that table in the same change. Also non-negotiable: a delivery applies unconditionally. Never add a "who has this cached?" gate, and never make a webhook trigger a fetch. **This is a build gate, not a convention.** `TestWebhookHandlersConsumeTheirPayload` (`internal/sync/webhook_payload_audit_test.go`) walks the dispatcher's own switch by AST.

  For EVERY event type it handles, it demands either a handler that provably reads the delivery body, followed through delegation, or a detailed `docs/webhooks/payload-unused/<event>.md`. It checks both ways. An excuse cannot outlive its reason. Teaching a handler to use its payload fails the build until that doc is deleted in the same change. Exceptions exist today, `organization` and `membership`. The mirror stores no membership state for either payload to land in.
- MARSHALLING — a JSON literal is a constant produces JSON text, or it is a bug.** Every other way of building it guesses about the values. `+` escapes nothing. `` `{"conclusion":` + frag + `}` `` is worse than `` `"sha":"` + sha + `"` ``. A quote or backslash in `frag` reshapes the document, not one string. `%s` is raw, and `%d` assumes a number. Even `%q` is GO quoting, not JSON, because it emits `\a`, `\v`, `\xNN` and `\UNNNNNNNN`, none of which JSON accepts. The moment a runtime value belongs in a document, the document is a Go value handed to `encoding/json`. `internal/guards` (`TestNoJSONSplices`) walks every `.go` file in the repo and fails the build on either shape. Its file header is the full rule. In tests the marshalling path is `writeGitHubJSON`, `mustJSONString`, `postWebhookJSON` and `fixtureRepo` (api), and `mustJSON` (sync, notify).
- **EVERY SENDS of the REQUEST THIS SERVICE IS ON THE DASHBOARD — no exceptions. It is a BUILD GATE.** A request nobody can see is a request nobody can account for. It spends rate-limit budget. It can be slow. It can fail. None of that reaches the chart an operator reads. Instrumenting call sites cannot hold that property, because it covers the calls someone remembered. `internal/auth` proved it by making unobserved GitHub calls per sign-in, invisible on the page they served. So the rule is about the CLIENT. It reports from its TRANSPORT (`internal/httpobs`), or it is a hole. `internal/guards.TestEveryOutboundClientIsObserved` finds every construct that can send: an `http.Client` or `httputil.ReverseProxy` literal, `http.DefaultClient`, and the package-level senders. It fails until each one is declared with what makes it visible. The uncharted surface is the dashboard's own INBOUND `/api/*`, which fills the chart with the act of viewing it. That gap is stated, not silent. docs/dashboard/request-visibility.md.
- **A LOST DELIVERY IS HERE of the THE QUIETEST FAILURE, AND ONE of the GITHUB NEVER RETRIES.** Miss a push. Every cache that delivery moves then serves its last absorbed answer for the full TTL, with nothing reporting a gap. The worst shape stops its own repair. A cached `behind_by: 0` is what makes pr-minder decide a PR needs no branch update. The PR then sits armed-to-merge until a human looks. 9.6h measured that. Mechanisms are required. The replayer (`internal/sync/replay.go`) reads the App's OWN failure log, `GET /app/hook/deliveries?status=failure`. It asks GitHub to re-send what never arrived: once per delivery id, a 24h lookback, 25 per cycle, logged. Separately, `compare_cache.base_tip_sha` records the base tip GitHub says an answer was computed against. A read can then refuse that answer, whatever happened to the flush. Never answer a gap with a shorter TTL. That hides the window. It does not close it. docs/webhooks/delivery-gaps.md.
- **A BRANCH TIP IS WORST of the RUINS of the DELIVERY of the LOST of the THE ANSWER A. Keeping it right is THIS SERVICE's job, not a client's.** A consumer cannot notice a delivery that never arrived. A "revalidate this for me" request from one is therefore the responsibility inverted. That was the first cut of this fix. It is rejected. Internal mechanisms stand in its place. Every delivery that STATES the tip applies it: a push's `after`, and a merged PR's `merge_commit_sha` for its base branch (`ApplyMergedBaseTip`, ordered against the row's own establishment time). And a stored tip that the mirror's own absorbed PR rows CONTRADICT is refetched rather than served (`GetCachedGitRefChecked`). That refetch is bounded to one per genuinely new disagreeing sha, because a PR's `base.sha` legitimately lags. PR rows work as evidence because they arrive on a DIFFERENT delivery. The branches list, the compare rows and `KnownBranchTip` do not, and `KnownBranchTip` reads these very rows. docs/cache/stale-tip-repair.md.
- **A DELIVERY IS A MOMENT of the OWN of the VIEW OF ITS. A LATE ONE CAN TRUTH of the OVERWRITE A NEWER.** Idempotence does not help. Applying an old payload is a correct, repeatable write of superseded state. A merged PR came back OPEN many seconds after its merge, from a redelivered pre-merge payload. It stayed open for many minutes. Only open PRs are retained. The close had therefore DELETED the row. A deleted row has nothing to lose a comparison against. Every close now leaves one (`pr_closures` plus the closing view's `updated_at`). Every open-PR write path refuses a view that cannot prove it postdates that. Fix this class at the WRITE, not in the replayer. Ordinary out-of-order delivery does the same damage. docs/webhooks/delivery-gaps.md.
- **GITHUB SENDS of the ORDERS NOTHING IT. THE DISPATCHER DOES.** Every delivery states the moment its view is from. It also states the SUBJECT it is a view of (`webhook.OrderOf`). The clock is always a GitHub-set payload field: `repository.pushed_at`, not `head_commit.timestamp`. No header carries one, and the tunnel's own headers describe our hop. Every delivery is applied on arrival. A per-subject **watermark** refuses anything older than a view already applied (`superseded`). A payload is a full snapshot of its subject, so applying only the newest view lands on the same last state. This is as applying them all in order. The subject grain is load-bearing. `status` keys sha plus CONTEXT. Keyed on the sha alone, one context's result discards another's. A superseded push still absorbs its commits, which are immutable facts a newer view never restates. All of it is counted, timed and shown on the Webhooks tab, because "significant disruption" needs a distribution, not a boolean. docs/webhooks/ordering.md.
- **App-identity principal (opt-in, for trusted first-party app callers)** — a request-time caller may send a **GitHub App JWT** in the `X-Mirror-Identity` header. `requireAuth` verifies it with `ghclient.VerifyAppIdentity` (`GET /app`), and caches the verdict per JWT. GitHub only answers 200 if the RS256 signature checks out against the app's public key. The assertion is therefore unforgeable. That caller then resolves to the principal `app:<id>`, skipping the per-user and fingerprint resolution fully, which an installation token cannot pass anyway. This exists because such a caller's installation tokens rotate hourly. A fingerprint principal loses its earned grants every hour. The app principal instead keeps **one stable grant set** across all the app's tokens. The `Authorization` token is still injected into the context for upstream fetches, probes and passthrough, so per-repo authorization against GitHub is unchanged. No identity header means the default per-user or fingerprint resolution above.
- **The cache contract (tiers)** — every data route is exactly one of three things. It is the GraphQL org-repos query, byte-identical and identity-test-locked. It is a cached REST route, whose state is absorbed and whose response is REBUILT with every URL field dropped. Or it is verbatim passthrough, uncached and debounced. There is no "correctly uncached" verdict. A route that still forwards is unfinished work. docs/cache/three-tier-contract.md — the tiers in full. The route families, the no-URL-keys invariant, and passthrough debouncing.
- **compression of the response of the + of the Timeline wire format**. `GET /api/timeline` serves a COLUMNAR binary payload to a caller naming `application/vnd.gsm.timeline.v1` EXACTLY, and readable JSON to everyone else. The JSON is safe only because **the chart REFUSES it**. `fetchTimelineBytes` sends one Accept and THROWS on any other content type. An earlier fallback made a drifted Accept a silent downgrade to several times the frames. `TestTimelineClientRefusesJSON` drives the BUILT module to pin that refusal. Deleting the JSON instead is a rejected fix, because it served operators and the fallback was the defect. The origin is grey-clouded, so the app gzips its own dashboard payloads (`internal/api/compress.go`). That covers buffered admin endpoints only, not the data plane, whose header contract is pinned and whose NDJSON stream must keep flushing. The FORMAT itself lives in js-snippets, and only the VOCABULARY is ours. See docs/timeline-wire-format.md for both halves of the library, the `wire:` tags. And why a layout change is a new version.

- **Installation tokens at rest (security note)** — the token-mint cache stores each minted installation token in SQLite (`install_token_cache.token`). This is the same trust domain as the traffic itself. The mirror already relays these exact tokens in cleartext on every request it proxies. The DB file sits on the same host, under the same access. The token's own short expiry bounds every row, about an hour, plus the serve-until cutoff. Expiry and LRU pruns rows, and flushed on installation events. Token values are never logged, because the request log records only method, path and disposition. They never appear in an error message either. Keep it that way when touching `respcache.go`.
- **OAuth relay (github.com login endpoints)** — `POST /login/oauth/access_token` and `POST /login/device/code` relay the browser-blocked `github.com` login endpoints, which are not on `api.github.com`. They share one core, `relayGitHubLogin` in `internal/api/oauth.go`. The pair covers the OAuth code-for-token exchange and the RFC 8628 device-authorization start. Each answer carries the mirror's CORS headers, so a purely client-side app can complete a login that GitHub's own login endpoints do not allow. The device flow's polling leg goes through the access_token route unchanged, under `grant_type` `urn:ietf:params:oauth:grant-type:device_code`. Its body is opaque bytes to the relay. Both routes are registered outside `requireAuth`, because the body is the credential: an OAuth `client_secret`, or just a public `client_id` for the device flow. There is no bearer token. They forward only the body and the content-negotiation headers, to fixed URLs (`githubOAuthTokenURL`, `githubDeviceCodeURL`), which are vars so a test can point them. This is at a fake. They do NOT copy GitHub's `Access-Control-*` headers, because corsMiddleware is the single CORS authority and a duplicate ACAO breaks the browser. This is why repo-nightmare's `TOKEN_PROXY` points here instead of at a standalone CORS proxy.
- **Admin truth browse, grants view + consistency check/reconcile** — `GET /api/cache/data` dumps global truth rows, or one principal's access grants with `?principal=`. `GET /api/cache/check[?org=]` re-fetches truth from GitHub through the App and diffs it. `?stream=1` gives live NDJSON progress, and `POST ?apply=true` reconciles. A GET is read-only, covers open PRs only, and answers 503 with no App. The admin Principals tab surfaces both as buttons. **docs/dashboard/operator-tooling.md** — the field-by-field comparison rules, the raced-during-check classification, and every apply-mode correction.
- **Dashboard = separate authz model** — the dashboard (`internal/api/dashboard.go`, served at `/`) authenticates a human through GitHub OAuth and authorizes by **login** (`ADMIN_LOGINS`). That is deliberately distinct from the data API's bearer-token and show model. It reports GLOBAL truth totals plus per-principal show standing. An admin also gets the Webhooks, Requests, Rate limit and Timeline tabs, the JSON-only `/api/jobs` and `/api/notifications`, and the **implementation brief** (`/api/brief`, plus its "Capture implementation brief" button under the uncached-routes table). The Webhooks tab additionally reports **missing App event subscriptions**. Those are the `ghdata.RequiredWebhookEvents` the App is not subscribed to, per GitHub's own answer (`AppAuthenticator.SubscribedEvents`, `GET /app`). Each one names what degrades without it. A missing subscription otherwise fails silently, and the affected caches just re-fetch forever. NEVER infer this from the delivery log. That log is row-capped, so on a busy fleet it spans minutes, and every low-frequency required event reads as unsubscribed. When it is unknowable, with no App or a failed lookup, the tab reports nothing rather than everything. The request log, rate meter and timeline ring are IN-MEMORY live views, not audit logs. All three reset on start. **docs/dashboard/dashboard.md** — the tabs, the payload shapes, the passthrough-reason vocabulary, and the sign-in-failure 400 rule.
- **TypeScript front-end** — the dashboard's ONLY source is `internal/api/web/src/*.ts`, compiled by `npm run build` to `internal/api/web/assets/*.js`. That JS is a gitignored, embedded build output. It is never committed and never hand-edited. Run the build before any Go build or test. `//go:embed` names each file, and a missing one fails to compile. See docs/dashboard/frontend.md. For the CI gates, the preview job, the harnesses, and where an added asset is wired.
- **Pointing `gh` at the mirror** — `GH_HOST=<host>` makes gh treat the mirror as GitHub Enterprise. REST then gains an `/api/v3` prefix, GraphQL moves to `/api/graphql`, and the token is read from `GH_ENTERPRISE_TOKEN`. `internal/api/ghecompat.go` canonicalises both paths ahead of the router, so one route table serves both spellings. The rewrite grants nothing: a prefixed request meets the same auth and show gates. docs/gh-cli.md.
- **Update-check endpoints** (`internal/api/updatechecks.go`) — `GET /.well-known/docker-updater/{health,pre-update}`, status code only, registered OUTSIDE `requireAuth`. That placement is load-bearing. An unrouted path here does not 404. It falls through to the passthrough proxy, which answers 401 for a tokenless request. docker-updater reads any non-404 as "implemented". Leaving these unregistered thus reports the container as permanently unhealthy. The health probe pings the cache DB (`Store.Ping`). The pre-update probe holds while `freshness.Manager.Busy()` reports a detached fetch in flight.
- **Build** — use `go-toolchain`, not `go build` or `go test` directly. Run `npm run build` first on a fresh checkout, and after editing `web/src/*.ts`. The JS it emits is gitignored, and `//go:embed` needs it on disk.
- **The image is a GOOS=cosmo APE. It needs a shell to start.** The kernel cannot exec an APE. This is because the file begins `MZqFpD=` rather than an ELF header. busybox therefore supplies `/bin/sh`. The entrypoint names it. An exec-form `ENTRYPOINT` gets ENOEXEC no matter what the image contains, on every host whose kernel has no APE `binfmt_misc` entry. The base stays distroless for its CA certificates. `/tmp` is writable because staging writes there. See [docs/APE-STAGING.md in gosmopolitan](https://github.com/wow-look-at-my/gosmopolitan/blob/master/docs/APE-STAGING.md).
- **`docker/imagecheck.test.ts` RUNS the image, and `publish-ghcr` is gated on it.** CI's `image-smoke` job only invokes `npm run test:image`, because the assertions belong in the suite and never in the YAML. `build` tests the host binary, and the publish job never started what it pushed. The first execution of the entrypoint was thus production. An image that cannot exec its own binary shipped green this way and 404'd the whole fleet. Never publish an image no job started. The suite needs docker and `build/server`, and FAILS rather than skips without them. Its last case is a negative control. It requires an execve of the binary to fail with ENOEXEC in a user namespace with its own empty `binfmt_misc`. On a kernel with no APE entry it also builds a variant with an exec-form entrypoint and requires that one NOT to start. The checks thus cannot pass for an image that merely happens to work. A runner host can carry an APE entry that the runner cannot see. The control therefore asks execve in a container whether the kernel has one, and never reads a `binfmt_misc` listing.

## Commands

- `go-toolchain` — runs mod tidy, vet, test, build (all-in-one)
- `sqlc generate` — regenerates `internal/database/dbgen/*.gen.go` (after editing `schema.sql` or `queries/*.sql`)
- `npm run build` — compiles `internal/api/web/src/*.ts` to the gitignored `internal/api/web/assets/*.js`. Run it on a fresh checkout before any Go build, and after editing the dashboard front-end.

## Environment Variables

- `GITHUB_APP_ID` (optional) — GitHub App ID. When it is set with a private key, the service signs in as this app for background work. That covers periodic refreshes and the source-of-truth fetch for the admin consistency check (`/api/cache/check`). It never serves a normal data-API request, which needs the caller's own `Authorization` header and answers 401 without it. Unset means periodic refreshes are disabled and the consistency check reports "unavailable" (503). Webhooks apply to global truth either way.
- `GITHUB_APP_PRIVATE_KEY` / `GITHUB_APP_PRIVATE_KEY_PATH` — the App's PEM private key (PKCS#1 or PKCS#8), inline (optionally `\n`-escaped) or as a file path (path wins). Required when `GITHUB_APP_ID` is set.
- `WEBHOOK_SECRET` — secret of the GitHub webhook HMAC
- `LISTEN_ADDR` — HTTP listen address (default `:8080`)
- `DB_PATH` — path of the SQLite database file (default `github-mirror.db`)
- `SUBSCRIPTIONS_DB_PATH` (optional) — the subscriber-notification config DB, a SEPARATE SQLite file the schema nuke never touches. Default derives from `DB_PATH`: strip a trailing `.db`, append `-subscriptions.db` (`github-mirror.db` -> `github-mirror-subscriptions.db`).
- `ALLOWED_ORIGINS` (optional) — comma-separated CORS allow-list for browser clients, such as the repo-nightmare PR viewer. It defaults to `*`, any origin, which is safe because the cache reveals data by the caller's proven GitHub access rather than by origin. A preflight `OPTIONS` is answered without auth. See `internal/api/cors.go`. The middleware also sets `Access-Control-Expose-Headers`: the `X-RateLimit-*` budget plus `X-GSM-Cache`, `X-GSM-Stale` and `X-GSM-Last-Fetched`. Without that list the CORS default hides every one of them from a cross-origin app. A REBUILT response has no upstream Expose-Headers list to inherit. A browser client can thus read none of them on a cache HIT. The proxy still deliberately keeps GitHub's own Expose-Headers on a passthrough. Repeated list-valued header fields combine, so a passthrough exposes the UNION, which only ever widens what a browser may read.
- `CACHE_MAX_ROWS` (optional) — per-table row ceiling for the response caches. It sets `ghdata.CacheMaxRows` at startup and defaults to `1000000`. It is one knob for every cache table. All but `git_commits_cache` are TTL-bounded, so for them the cap is only a runaway safety net. `git_commits_cache` holds immutable rows with no TTL, and is the one table that actually grows to the ceiling. A value that is unparseable or a bounded number of fails startup.
- `PASSTHROUGH_DEBOUNCE` (optional) — how long an eligible uncacheable READ is held, as a Go duration string, so same concurrent requests share one upstream call. It defaults to `5s`. `0` disables coalescing and forwards immediately. A value that is unparseable, negative, or above 30s fails startup. The window adds latency to every uncacheable read, so a fat-fingered `5m` must fail loudly at boot rather than wedge the API. See the tier-3 passthrough-debouncing paragraph.
- `REFRESH_INTERVAL` (optional) — periodic fleet-refresh cadence as a Go duration string (default `6h`). The first cycle always runs immediately at startup regardless of the interval. A value that is unparseable or not positive fails startup.
- `WEBHOOK_REPLAY_INTERVAL` (optional) — how frequently the delivery-gap replayer asks GitHub to re-send a delivery it never received. It defaults to `5m`, with the first cycle at startup, because a start is itself such a window. `0` disables recovery and the server warns. An unset `GITHUB_APP_ID` does the same, because the failure log is a JWT-authenticated app-level endpoint. An unparseable or negative value fails startup. See docs/webhooks/delivery-gaps.md.
- `GITHUB_OAUTH_CLIENT_ID` / `GITHUB_OAUTH_CLIENT_SECRET` (optional) — GitHub OAuth App credentials for dashboard login. Unset leaves the dashboard rendering with sign-in disabled. Register the OAuth App's callback as `<BASE_URL>/auth/callback`.
- `SESSION_SECRET` (optional) — HMAC key for session cookies. Unset means a random per-process key, so sessions reset on start. Set it in production.
- `ADMIN_LOGINS` (optional) — comma-separated logins that get the admin dashboard views: all principals, truth browse, and the consistency check. It defaults to `PazerOP` and is case-insensitive.
- `BASE_URL` (optional) — public base URL, such as `https://github-state-mirror.pazer.io`, used to build the OAuth `redirect_uri`. When unset it is derived from the request, honoring `X-Forwarded-Proto`.

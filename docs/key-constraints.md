# Key Constraints

- **No migrations, and nothing to declare** — `schema.sql` is hashed with comments scrubbed and whitespace normalized (`internal/database/fingerprint.go`). A DB recording a different hash is nuked and recreated on open. Editing a table nukes. Editing a comment does not, and nothing else nukes at all. A data problem is Reconcile's job, not a nuke's. The number this replaced was hand-maintained, and a change that forgot it deployed against the table it no longer described. History: docs/schema-history.md
- **sqlc codegen** — run `sqlc generate` after modifying `schema.sql` or `queries/*.sql`
- **Freshness/data separation** — `internal/freshness/` must never import GitHub-specific packages
- **Lazy fetches are detached, backoff-gated, and drained** — `freshness.Manager.doFetch` runs the fetch. Its metadata writes on a `context.WithoutCancel`-derived context, bounded only by `fetchSafetyTimeout` (5m). A client that aborts its request thus cannot kill the shared multi-page org-repos fetch mid-flight, nor stop the result being stored. A short caller deadline is deliberately NOT re-applied, because the old webhook-deadline re-application killed fetches half-done. Every detached fetch is tracked in an inflight WaitGroup. `Manager.Drain(timeout)` waits for them, and `cmd/server` calls it after `ListenAndServe` returns, BEFORE `db.Close()`. A fetch thus can never write to a closed DB at shutdown. An error-state row inside its `retry_after` window is NOT re-fetched by a lazy caller. `EnsureFreshOutcome` reports the stored error instead. A failing upstream is thus not hammered on every request. A deliberate refresh (a periodic trigger) bypasses the backoff. When `/graphql` serves the stale cache after a refresh failure it sets the `X-GSM-Stale: true` and `X-GSM-Last-Fetched` response headers, and WARN-logs with the principal. Headers only: the body stays identity-test-identical.
- **One global truth, revealed by permission (replaces per-actor isolation)** — the security boundary is the Show LAYER, not storage. Revealing `owner/repo` to a principal needs the repo to be public, a live grant, or a live probe with THAT principal's own token. Fail-closed rules must not regress. Unknown visibility counts as private. Only an authoritative denial is cached. Grants expire. A list-sync REPLACE-syncs. docs/reveal-layer.md — principal resolution, the App-identity path, and the background App credential.
- **APPLY THE PAYLOAD. INVALIDATION IS THE LAST RESORT.** This is the single most-violated rule in this repo. Every violation looks the same. GitHub hands us the new value in the delivery. We THROW IT AWAY and delete a row. We then buy the same fact back with a second HTTP request we did not need.

  A webhook is not a cache-busting ping. It is the answer. **The procedure, for every handler and every cached route, in order.** First: does the payload carry the new value? WRITE IT. Second: does it carry enough to DERIVE it?

  Derive it and write that. Third, only if neither holds, you may invalidate. That covers an unparseable body, or a change whose result the payload genuinely does not state, such as a rename or a recomputed `mergeable`. Then say in a comment WHY the payload cannot answer. "Invalidate, the next reader will refetch" is a bug report, not a design. A push alone hands you `ref` and `after`, which is the branch's exact new tip.

  It also hands you `before`, `created`/`deleted`/`forced`, `base_ref`, `repository.default_branch`, and up to 2,048 full commit objects. See docs/webhooks/dispatch.md for the per-event matrix. The COALESCE rules that keep a webhook from blanking known state, and the routes still violating this. Every surviving response-cache flush is inventoried in docs/webhooks/invalidations.md with a verdict: justified, or owed with the conversion named. The count can only go down, and a new flush belongs in that table in the same change. Also non-negotiable: a delivery applies unconditionally.

  Never add a "who has this cached?" gate, and never make a webhook trigger a fetch. **This is a build gate, not a convention.** `TestWebhookHandlersConsumeTheirPayload` (`internal/sync/webhook_payload_audit_test.go`) walks the dispatcher's own switch by AST. For EVERY event type it handles, it demands either a handler that provably reads the delivery body, followed through delegation, or a detailed `docs/webhooks/payload-unused/<event>.md`. It checks both ways. An excuse cannot outlive its reason.

  Teaching a handler to use its payload fails the build until that doc is deleted in the same change. Exceptions exist today, `organization` and `membership`. The mirror stores no membership state for either payload to land in.
- **MARSHALLING produces JSON text — a JSON literal is a constant, or it is a bug.** Every other way of building it guesses about the values. `+` escapes nothing. `` `{"conclusion":` + frag + `}` `` is worse than `` `"sha":"` + sha + `"` ``. A quote or backslash in `frag` reshapes the document, not one string. `%s` is raw, and `%d` assumes a number. Even `%q` is GO quoting, not JSON, because it emits `\a`, `\v`, `\xNN` and `\UNNNNNNNN`, none of which JSON accepts. The moment a runtime value belongs in a document, the document is a Go value handed to `encoding/json`. `internal/guards` (`TestNoJSONSplices`) walks every `.go` file in the repo and fails the build on either shape. Its file header is the full rule. In tests the marshalling path is `writeGitHubJSON`, `mustJSONString`, `postWebhookJSON` and `fixtureRepo` (api), and `mustJSON` (sync, notify).
- **THIS SERVICE SENDS (EVERY) (REQUEST) IS ON THE DASHBOARD — no exceptions. It is a BUILD GATE.** A request nobody can see is a request nobody can account for. It spends rate-limit budget. It can be slow. It can fail. None of that reaches the chart an operator reads. Instrumenting call sites cannot hold that property, because it covers the calls someone remembered. `internal/auth` proved it by making unobserved GitHub calls per sign-in, invisible on the page they served. So the rule is about the CLIENT. It reports from its TRANSPORT (`internal/httpobs`), or it is a hole. `internal/guards.TestEveryOutboundClientIsObserved` finds every construct that can send: an `http.Client` or `httputil.ReverseProxy` literal, `http.DefaultClient`, and the package-level senders. It fails until each one is declared with what makes it visible. The uncharted surface is the dashboard's own INBOUND `/api/*`, which fills the chart with the act of viewing it. That gap is stated, not silent. docs/dashboard/request-visibility.md.
- **A LOST DELIVERY IS QUIETEST FAILURE HERE (THE), AND NEVER RETRIES ONE (GITHUB).** Miss a push. Every cache that delivery moves then serves its last absorbed answer for the full TTL, with nothing reporting a gap. The worst shape stops its own repair. A cached `behind_by: 0` is what makes pr-minder decide a PR needs no branch update. The PR then sits armed-to-merge until a human looks. 9.6h measured that. Mechanisms are required. The replayer (`internal/sync/replay.go`) reads the App's OWN failure log, `GET /app/hook/deliveries?status=failure`. It asks GitHub to re-send what never arrived: once per delivery id, a 24h lookback, 25 per cycle, logged. Separately, `compare_cache.base_tip_sha` records the base tip GitHub says an answer was computed against. A read can then refuse that answer, whatever happened to the flush. Never answer a gap with a shorter TTL. That hides the window. It does not close it. docs/webhooks/delivery-gaps.md.
- **A BRANCH TIP IS A LOST DELIVERY RUINS WORST (ANSWER) (THE). Keeping it right is THIS SERVICE's job, not a client's.** A consumer cannot notice a delivery that never arrived. A "revalidate this for me" request from one is therefore the responsibility inverted. That was the first cut of this fix. It is rejected. Internal mechanisms stand in its place. Every delivery that STATES the tip applies it: a push's `after`, and a merged PR's `merge_commit_sha` for its base branch (`ApplyMergedBaseTip`, ordered against the row's own establishment time). And a stored tip that the mirror's own absorbed PR rows CONTRADICT is refetched rather than served (`GetCachedGitRefChecked`). That refetch is bounded to one per genuinely new disagreeing sha, because a PR's `base.sha` legitimately lags. PR rows work as evidence because they arrive on a DIFFERENT delivery. The branches list, the compare rows and `KnownBranchTip` do not, and `KnownBranchTip` reads these very rows. docs/cache/stale-tip-repair.md.
- **A DELIVERY IS MOMENT of the A ITS OWN (OF) (VIEW). A LATE ONE CAN A NEWER TRUTH (OVERWRITE).** Idempotence does not help. Applying an old payload is a correct, repeatable write of superseded state. A merged PR came back the seconds of a later OPEN after its merge, from a redelivered pre-merge payload. It stayed open for many minutes. Only open PRs are retained. The close had therefore DELETED the row. A deleted row has nothing to lose a comparison against. Every close now leaves one (`pr_closures` plus the closing view's `updated_at`). Every open-PR write path refuses a view that cannot prove it postdates that. Fix this class at the WRITE, not in the replayer. Ordinary out-of-order delivery does the same damage. docs/webhooks/delivery-gaps.md.
- **NOTHING IT SENDS (GITHUB) (ORDERS). THE DISPATCHER DOES.** Every delivery states the moment its view is from. It also states the SUBJECT it is a view of (`webhook.OrderOf`). The clock is always a GitHub-set payload field: `repository.pushed_at`, not `head_commit.timestamp`. No header carries one, and the tunnel's own headers describe our hop. Mechanisms follow. A per-subject **reorder window** (`WEBHOOK_REORDER_WINDOW`, 2s) sorts what lands close together and applies it oldest-first. A per-subject **watermark** refuses anything older than a view already applied (`superseded`). The subject grain is load-bearing. `status` keys sha plus CONTEXT. Keyed on the sha alone, one context's result discards another's. A superseded push still absorbs its commits, which are immutable facts a newer view never restates. All of it is counted, timed and shown on the Webhooks tab, because "significant disruption" needs a distribution, not a boolean. docs/webhooks/ordering.md.
- **App-identity principal (opt-in, for trusted first-party app callers)** — a request-time caller may send a **GitHub App JWT** in the `X-Mirror-Identity` header. `requireAuth` verifies it with `ghclient.VerifyAppIdentity` (`GET /app`), and caches the verdict per JWT. GitHub only answers 200 if the RS256 signature checks out against the app's public key. The assertion is therefore unforgeable. That caller then resolves to the principal `app:<id>`, skipping the per-user and fingerprint resolution fully, which an installation token cannot pass anyway. This exists because such a caller's installation tokens rotate hourly. A fingerprint principal loses its earned grants every hour. The app principal instead keeps **one stable grant set** across all the app's tokens. The `Authorization` token is still injected into the context for upstream fetches, probes and passthrough, so per-repo authorization against GitHub is unchanged. No identity header means the default per-user or fingerprint resolution above.
- **The cache contract (tiers)** — every data route is exactly one of three things. It is the GraphQL org-repos query, byte-identical and identity-test-locked. It is a cached REST route, whose state is absorbed and whose response is REBUILT with every URL field dropped. Or it is verbatim passthrough, uncached and debounced. There is no "correctly uncached" verdict. A route that still forwards is unfinished work. docs/cache/three-tier-contract.md — the tiers in full, the route families, the no-URL-keys invariant, and passthrough debouncing.
- **Timeline wire format + response compression** — `GET /api/timeline` serves a COLUMNAR binary payload to a caller naming `application/vnd.gsm.timeline.v1` EXACTLY, and readable JSON to everyone else. The JSON is safe only because **the chart REFUSES it**. `fetchTimelineBytes` sends one Accept and THROWS on any other content type. An earlier fallback made a drifted Accept a silent downgrade to several times the frames. `TestTimelineClientRefusesJSON` drives the BUILT module to pin that refusal. Deleting the JSON instead is a rejected fix, because it served operators and the fallback was the defect. The origin is grey-clouded, so the app gzips its own dashboard payloads (`internal/api/compress.go`). That covers buffered admin endpoints only, not the data plane, whose header contract is pinned and whose NDJSON stream must keep flushing. The FORMAT itself lives in js-snippets, and only the VOCABULARY is ours. See docs/timeline-wire-format.md for both halves of the library, the `wire:` tags. And why a layout change is a new version.

- **Installation tokens at rest (security note)** — the token-mint cache stores each minted installation token in SQLite (`install_token_cache.token`). This is the same trust domain as the traffic itself. The mirror already relays these exact tokens in cleartext on every request it proxies. The DB file sits on the same host with the same access. The token's own short bounds every row (~1h) expiry plus the serve-until cutoff. Rows are pruned on write (expired + LRU) and flushed on installation events. Token values are never logged (the request log records method/path/disposition only) and never appear in error messages. Keep it that way when touching `respcache.go`.
- **OAuth relay (github.com login endpoints)** — `POST /login/oauth/access_token` and `POST /login/device/code` (`internal/api/oauth.go`) relay the browser-blocked `github.com` login endpoints with the mirror's CORS headers, outside `requireAuth`. A client-side app can sign in. The relay also SUPPLIES the client secret (`OAUTH_RELAY_SECRETS`): a browser app cannot hold one and GitHub Apps have no PKCE. This is the only server in that exchange. docs/oauth-relay.md — the full contract, what is forwarded untouched, and the unconfigured-app failure.
- **Admin truth browse, grants view + consistency check/reconcile** — `GET /api/cache/data` dumps global truth rows (or one principal's access grants with `?principal=`). `GET /api/cache/check[?org=]` re-fetches truth from GitHub via the App and diffs it, `?stream=1` for live NDJSON progress, `POST ?apply=true` to reconcile. Read-only GET, open PRs only, 503 with no App. Surfaced as the admin Principals tab's buttons. Full field-by-field comparison rules, the raced-during-check classification, and every apply-mode correction: **docs/dashboard/operator-tooling.md**.
- **Dashboard = separate authz model**. The dashboard (`internal/api/dashboard.go`, served at `/`) authenticates a human via GitHub OAuth and authorizes by **login** (`ADMIN_LOGINS`), deliberately distinct from the data API's bearer-token + show model. It reports GLOBAL truth totals plus per-principal show standing. Admins also get the Webhooks / Requests / Rate limit / Timeline tabs (the Webhooks tab additionally reports **missing App event subscriptions**. The `ghdata.RequiredWebhookEvents` the App is not subscribed to per GitHub's own answer (`AppAuthenticator.SubscribedEvents`, `GET /app`), each with what degrades without it. A missing subscription otherwise fails silently, the affected caches just re-fetching forever. NEVER infer this from the delivery log: that log is row-capped. Do this so on a busy fleet it spans minutes and every low-frequency required event reads as unsubscribed. Unknowable — no App, or a failed lookup — reports nothing rather than everything), the JSON-only `/api/jobs` and `/api/notifications`, and the **implementation brief** (`/api/brief` + its "Capture implementation brief" button under the uncached-routes table). The request log, rate meter, and timeline ring are IN-MEMORY (live views, not audit logs) and reset on start. Tabs, payload shapes, the passthrough-reason vocabulary, and the sign-in-failure 400 rule: **docs/dashboard/dashboard.md**.
- **TypeScript front-end** — the dashboard's ONLY source is `internal/api/web/src/*.ts`. `npm run build` (tsc) compiles it to `internal/api/web/assets/*.js`, which is a **gitignored build output that is never committed**, embedded via `//go:embed`. Work only in the `.ts` — the `.js` is disposable, regenerated on demand, not hand-edited and never added to git.

  The embed names each `.js` file, so a missing one is a Go COMPILE error: `npm run build` must run before any Go build or test (CI's `build` job runs `npm ci && npm run build` ahead of `go-toolchain` for exactly this reason). CI's `web-check` job is the type-check gate (`npm ci` + `npm run build` on the locked toolchain, tsc exits non-zero on any error) and it FAILS.

  If any generated `.js` is tracked (`git ls-files internal/api/web/assets/*.js` must come back empty) — so a second, staleable copy of the front-end can never re-enter the tree. Hand-written `assets/style.css` stays tracked. `assets/demo-data.js` is preview-only (NOT embedded). The CI `preview` job injects it to deploy a backend-free styling preview to buildhost per branch. Each `src/*.ts` emits its own standalone ES module loaded by its own `<script type="module">` tag in `index.html`.

  `rate-meter.ts` self-registers the `<rate-meter>` web component, `timeline.ts` self-registers `<gsm-timeline>` (types for its buildhost-URL component import live in the interim ambient shim `src/js-snippets-timeline.d.ts` — types only, keep it minimal). Adding an asset file means wiring it in **three** places. The `//go:embed` + hashed-URL machinery in `internal/api/dashboard.go`, the `index.html` script tag, and the `preview` job's copied-assets list in `ci.yml`.

  The node TEST HARNESS (`internal/api/testdata/browsercheck.ts` — the real-browser end-to-end frame check) is TypeScript too, type-checked against `src/` by `npm run check:harness` (`tsconfig.harness.json`, noEmit — node runs the `.ts` directly, so there is no build step and nothing lands in `assets/`). CI's `web-check` runs it, so a changed export signature fails the build instead of surfacing mid-measurement at runtime. `testdata/dashboardcheck.test.ts` is the second browser harness (`npm run test:dashboard`).

  It serves the built dashboard the way the preview job does and asserts from COMPUTED STYLE. That STYLE chrome the code hides with `el.hidden` is really off screen. An author `display` outranks the UA's `[hidden]` rule, which is why `style.css` carries `[hidden] { display: none !important }` and why nothing off-browser can see the difference. Playwright (both harnesses) is deliberately NOT a devDependency — `testdata/playwright.d.ts` is a minimal types-only shim so `npm ci` stays light.

- **OAuth relay (github.com login endpoints)** — `POST /login/oauth/access_token` and `POST /login/device/code` relay the browser-blocked `github.com` login endpoints, which are not on `api.github.com`. They share one core, `relayGitHubLogin` in `internal/api/oauth.go`. The pair covers the OAuth code-for-token exchange and the RFC 8628 device-authorization start. Each answer carries the mirror's CORS headers, so a purely client-side app can complete a login that GitHub's own login endpoints do not allow. The device flow's polling leg goes through the access_token route unchanged, under `grant_type` `urn:ietf:params:oauth:grant-type:device_code`. Its body is opaque bytes to the relay. Both routes are registered outside `requireAuth`, because the body is the credential: an OAuth `client_secret`, or just a public `client_id` for the device flow. There is no bearer token. They forward only the body and the content-negotiation headers, to fixed URLs (`githubOAuthTokenURL`, `githubDeviceCodeURL`). These are vars so a test can point them at a fake. They do NOT copy GitHub's `Access-Control-*` headers, because corsMiddleware is the single CORS authority and a duplicate ACAO breaks the browser. This is why repo-nightmare's `TOKEN_PROXY` points here instead of at a standalone CORS proxy.

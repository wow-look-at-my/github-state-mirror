# Subscriber notifications (`internal/notify`)

The rules that must not regress, extracted verbatim from CLAUDE.md.

- **Subscriber notifications (`internal/notify`) — config DB, reveal-gated fan-out, drained delivery** — the rules that must not regress:
  1. **Subscriptions are CONFIG in their own SQLite file, not nuked.** The schema-change-nukes doctrine applies ONLY to the main cache DB. The subscriptions DB (`SUBSCRIPTIONS_DB_PATH`, default `DeriveDBPath(DB_PATH)` = strip trailing `.db` + `-subscriptions.db`) is opened with `CREATE TABLE IF NOT EXISTS` and may only ever evolve ADDITIVELY (new columns with defaults) so old files keep working under new binaries. Its queries are **hand-rolled SQL inside `internal/notify`** — a deliberate, documented exception to the sqlc doctrine: `sqlc.yaml` targets the main cache DB's schema. A second codegen target for one small config table is not worth the entanglement.
  2. **Reveal-gated, fail-closed fan-out.** A subscription is notified about a repo ONLY if its principal can read it via the reveal layer's NON-PROBING fast paths at delivery time. This is public visibility in global truth, or a live grant (`AccessChecker` = `GetRepoInsensitive` + `HasGrant`, satisfied by `ghdata.Store`). There is NO per-notification probe (no caller token exists at delivery time) and no deny-cache involvement. Unknown/absent visibility = private, and a gate-store error gates the notification. A private repo's activity must NEVER reach an unauthorized principal.
  3. **Detached, tracked, drained delivery.** Notifier work runs on `context.Background`-derived contexts with bounded timeouts (the freshness-fetch pattern), tracked in a WaitGroup behind a mutex-guarded `track()` (closes the Add-vs-Wait race). `Notifier.Drain(timeout)` stops new work, cuts pending backoff sleeps, and waits out in-flight deliveries — `cmd/server` drains it alongside the freshness manager BEFORE closing the DBs. It closes the subscriptions DB after the main one. `NotifyIngest` returns immediately (the GitHub webhook response never waits on subscriber POSTs). Only `applied`/`invalidated` dispositions and single-owner/repo deliveries notify (repo-less `installation` events are skipped).
  4. **Bounded retries + auto-disable.** ~8 concurrent POSTs, attempts each (~8s per try, ~1s/~4s backoff). A terminal failure bumps `consecutive_failures` (short `last_error`, not the secret). At 10 the subscription auto-disables (`active=0`, `disabled_reason` set, WARN log). Success resets the counter. `PATCH {"active": true}` is the re-enable path (resets counter, clears reason).
  5. **Secrets at rest.** Subscription secrets are stored plaintext to sign every delivery (`X-Hub-Signature-256` over the exact body, per try) — the same trust domain as `install_token_cache` tokens. They are never logged and never returned by any API response (`subscriptionJSON` structurally has no secret field).
  6. **`/_mirror/*` is the RESERVED mirror-native namespace** — GitHub has no underscore-prefixed top-level paths and chi routes beat the NotFound passthrough. As a result, it can never collide with proxied GitHub traffic. New mirror-native endpoints belong under it. The CRUD routes live INSIDE requireAuth (per-principal ownership. A foreign id answers 404 — no existence leak), skip the reveal layer (not repo reads), and stay out of the GitHub request log. Observability is the admin-only `GET /api/notifications` (in-memory ring + counters, requestLog stance) — JSON only, no dashboard tab, no TS.
  7. **The activity log (`internal/notify/ring.go`)** is the in-memory, bounded record of recent delivery attempts plus cumulative counters -- the requestLog stance: a live operational view. This is not an audit log. Deliberately unpersisted (it resets on start). Methods are safe for concurrent use and no-op on a nil receiver. `OutcomeDisabled` is a terminal failure that also tripped the auto-disable threshold. `OutcomeGated` means the show gate blocked the notification (no public visibility and no live grant -- or the gate can not decide, which fails closed). `Attempt.PrincipalName` is the principal's recorded display name. The notify package never sets it -- the admin handler joins it from `actor_identities` when serving the activity view (display-only decoration).

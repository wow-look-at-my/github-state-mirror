# Webhook -> response-cache invalidation matrix

Which delivery flushes which cached-response rows, at which grain. Extracted
verbatim from CLAUDE.md, which keeps the invariant ("webhooks always apply")
and a pointer here.

The code is `internal/sync/webhook_invalidate.go`
(`invalidateResponseCaches` / `invalidateForPush`).

The dispatcher also maintains the response caches (disposition-neutral, best-effort; round 2 made the grain **per-ref** wherever the payload names the moved refs — `invalidateResponseCaches`/`invalidateForPush`): a `push` flushes the PUSHED REF's rows in the ref-keyed tables — `contents_cache` and `commits_list_cache` per ref, PLUS their empty-ref spelling when the pushed ref IS the payload's `default_branch` (an empty ref key means "the default branch", so a default-branch push moves both spellings; a payload that doesn't say which branch is the default falls back repo-wide for exactly these two tables), `compare_cache` rows naming the ref on EITHER side (`base_ref`/`head_ref` — a 404 unknown-ref verdict clears the moment a push creates the ref), and `commit_ci_cache` rows keyed by the ref's verbatim spelling — while `pull_files_cache`, `branches_list_cache`, and `pull_diff406_cache` stay REPO-WIDE on every push (no per-ref signal: a base push moves merge-base-relative file lists and can move any PR's three-dot diff across the 406 boundary, and any push edits the branch listing); a push payload with no usable ref keeps the old conservative whole-repo flush for all the ref-keyed tables. Every per-ref branch/tag flush covers the ref in EVERY spelling GitHub accepts (`refSpellings`: the bare name plus `heads/<name>`/`refs/heads/<name>`, or the tags forms) — rows key the verbatim requested spelling, so a bare-name-only flush would leave the qualified spellings serving stale; sha flushes stay single-spelling (an abbreviated-sha-keyed row is bounded by the 24h TTL, and surveyed consumers send full hex). `status`/`check_run`/`check_suite` flush per the refs the payload names — the head branch(es) + the sha itself for `commit_ci_cache` (rows key the verbatim requested ref, so branch-form and sha-form rows both go) and the sha's `workflow_runs_cache` pages — falling back repo-wide for both when the payload names none. `workflow_job` deliveries flush the job's `head_sha`'s `workflow_runs_cache` pages (repo-wide when absent) — and this runs for EVERY delivery, BEFORE the disposition logic, so the `queued`/`waiting` jobs the apply side drops as `ignored` still flush (a queued job is a run the cached listing may not have shown yet). `workflow_run` deliveries flush the run's `head_sha`'s `workflow_runs_cache` pages the same way (repo-wide when absent) — the ONLY signal for a `startup_failure` run, which creates no jobs, check runs, or statuses; the truth side has no `workflow_run` handler, so the delivery still records as `ignored` (invalidation precedes disposition, the queued-workflow_job precedent). `pull_request`/`pull_request_review` events flush that ONE PR's `pull_files_cache` pages, its `closed_pull_cache` doc, and its `pull_diff406_cache` verdict (head pushes — including fork heads whose push events never arrive — base retargets, reopens; PRNumber-guarded, any action). `repository` flushes EVERYTHING repo-wide: all of the above plus the `pulls_list_cache` marker, the `closed_pull_cache` docs, and the `git_commit_miss_cache` markers (`pull_request` events deliberately do NOT touch the list marker — they maintain the PR rows the marker vouches for; and a `push` deliberately never touches closed docs — it cannot mutate a closed PR). Positive `git_commits_cache` rows are immutable and are NEVER invalidated; the git-commit 404 MISS markers are instead cleared by the absorb path itself (every real commit upsert un-misses its sha — `ghdata.upsertGitCommit`, the single funnel all absorb paths share). Unparseable payloads always fall back to the repo-wide flush. `installation`/`installation_repositories` flush the installation's `install_token_cache` AND `repo_installation_cache` rows. `workflow_job` deliveries (`in_progress`/`completed` only; `queued`/`waiting` dropped as `ignored` — after the cache flush above) record job state in the global `workflow_jobs` table (admin-only `GET /api/jobs`; out-of-order tolerant upsert; completed rows pruned once BOTH their `completed_at` and `updated_at` are 14 days past — retention keys on the last webhook touch too, because the row is the upsert guard's only memory: a prune keyed on `completed_at` alone deleted a just-recorded old completed event (delivery replays legitimately re-send those) and let a late in_progress resurrect the job as a phantom running row — the 2026-07-17 CI incident). **Operator action required**: the GitHub App must be subscribed to the `workflow_job` event for that table to fill — and to the `workflow_run` event for the startup-failure `workflow_runs_cache` flush above (until it is, that staleness window is bounded by the cache's 24h TTL).

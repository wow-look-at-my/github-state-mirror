# Webhook -> response-cache invalidation matrix

Which delivery flushes which cached-response rows, at which grain. Extracted verbatim from CLAUDE.md, which keeps the invariant ("webhooks always apply") and a pointer here.

The code is `internal/sync/webhook_invalidate.go` (`invalidateResponseCaches` / `invalidateForPush`).

The dispatcher also maintains the response caches (disposition-neutral, best-effort. Round 2 made the grain **per-ref** wherever the payload names the moved refs — `invalidateResponseCaches`/`invalidateForPush`). A `push` flushes the PUSHED REF's rows in the ref-keyed tables:

- `contents_cache` and `commits_list_cache` per ref. Their empty-ref spelling goes too when the pushed ref IS the payload's `default_branch`. (An empty ref key means "the default branch", so a default-branch push moves both spellings. A payload that does not say which branch is the default falls back repo-wide for these tables.)
- `compare_cache` rows naming the ref on EITHER side (`base_ref`/`head_ref` — a 404 unknown-ref verdict clears the moment a push creates the ref).
- `commit_ci_cache` rows keyed by the ref's verbatim spelling.

`pull_files_cache`, `branches_list_cache`, and `pull_diff406_cache` stay REPO-WIDE on every push. They have no per-ref signal. A base push moves merge-base-relative file lists. It can also move any PR's three-dot diff across the 406 boundary. Any push edits the branch listing. A push payload with no usable ref keeps the old conservative whole-repo flush for all the ref-keyed tables. Every per-ref branch/tag flush covers the ref in EVERY spelling GitHub accepts (`refSpellings`: the bare name plus `heads/<name>`/`refs/heads/<name>`, or the tags forms) — rows key the verbatim requested spelling. As a result, a bare-name-only flush will leave the qualified spellings serving stale. Sha flushes stay single-spelling (an abbreviated-sha-keyed row is bounded by the 24h TTL, and surveyed consumers send full hex). `status`/`check_run`/`check_suite` flush per the refs the payload names — the head branch(es) + the sha itself for `commit_ci_cache` (rows key the verbatim requested ref, so branch-form and sha-form rows both go). The sha's `workflow_runs_cache` pages — falling back repo-wide for both when the payload names none. Within those refs the `commit_ci_cache` grain is the KIND, because the surfaces are disjoint upstream. A commit status never appears in a check-runs listing and a check run never appears in a commit's statuses. As a result, a check delivery moves only the `check_runs` rows and a `status` delivery only the `status`/`statuses_list` rows. And a `status` delivery does not flush its own kinds at all where it can answer them. It CARRIES the status, so `SettleCommitCIFromStatus` REWRITES the stored documents from the payload (append-only statuses, the combined doc's latest-per-context oldest-first ordering, the documented rollup). It drops only the pages that cannot provably hold the result. The full rules, the measurement they rest on, and the identity pin are in docs/webhooks/invalidations.md. `workflow_job` deliveries flush the job's `head_sha`'s `workflow_runs_cache` pages (repo-wide when absent). This runs for EVERY delivery, BEFORE the disposition logic, so the `queued`/`waiting` jobs the apply side drops as `ignored` still flush (a queued job is a run the cached listing may not have shown yet). `workflow_run` deliveries flush the run's `head_sha`'s `workflow_runs_cache` pages the same way (repo-wide when absent). That is the ONLY signal for a `startup_failure` run, which creates no jobs, check runs, or statuses. They ALSO apply the run's own state to the `workflow_runs` truth table, so the delivery records as `applied`. **The repo-wide runs LISTING is deliberately absent from this whole matrix.** It is rebuilt from those truth rows. `workflow_run` and `workflow_job` deliveries MAINTAIN them one run at a time. A delivery that moved one run thus leaves every other run's answer served. Clearing the repo's listings on each job event will be invalidate-and-refetch. The thing this document's first sentence says the dispatcher does not do — and `TestDispatch_RunStateEvents_NeverClearTheListing` fails if it comes back. Only `repository` events invalidate there (rows AND the completeness proof), because a rename/delete/visibility change makes the rows themselves wrong rather than stale. `pull_request`/`pull_request_review` events flush that ONE PR's caches. Those are its `pull_files_cache` pages, its `closed_pull_cache` doc, and its `pull_diff406_cache` verdict (head pushes — including fork heads whose push events never arrive — base retargets, reopens. PRNumber-guarded, any action). A `pull_request` delivery reporting a MERGE additionally APPLIES the base branch's new tip to `git_ref_cache` (`merge_commit_sha`, every spelling, only when the merge postdates the row's own `fetched_at`). The base branch's push states the same fact. The mirror hears it twice on purpose. Losing the delivery that states a branch tip is what wedged xml-validator#10 (docs/cache/stale-tip-repair.md). An OPEN PR's `merge_commit_sha` is the test-merge commit, on no branch, and is never read as a tip. `repository` flushes EVERYTHING repo-wide. That is all of the above plus the `pulls_list_cache` marker and the `closed_pull_cache` docs. It also takes the `git_commit_miss_cache` markers and the repo's `hooks_cache` listings. It is the ONLY delivery that reaches those. This is because GitHub's `meta` event names a hook deletion but is sent only to the hook being deleted. As a result, another hook's removal never arrives here. Their real bounds are the short TTL and the flush the mirror applies when it PROXIES a hook write. That flush crosses every credential, since one caller's hook change moves everyone's answer. (`pull_request` events deliberately do NOT touch the list marker — they maintain the PR rows the marker vouches for. And a `push` deliberately never touches closed docs — it cannot mutate a closed PR). Positive `git_commits_cache` rows are immutable and are NEVER invalidated. The git-commit 404 MISS markers are instead cleared by the absorb path itself (every real commit upsert un-misses its sha — `ghdata.upsertGitCommit`, the single funnel all absorb paths share). Unparseable payloads always fall back to the repo-wide flush. `label` deliveries flush the repo's `label_cache` rows on EVERY action, before the disposition logic — the grain is the repo. An `edited` can RENAME (names in one delivery), and one label answers under every requested spelling. A match on the name the payload happens to carry will thus miss rows. The `PATCH`/`DELETE` the mirror proxies on the same path flush it too, BEFORE forwarding. A caller thus cannot read back its own stale write in the seconds before the delivery lands. `installation`/`installation_repositories` flush the installation's `install_token_cache` AND `repo_installation_cache` rows by id, and — because neither carries an id to match on. ALSO sweep every cached "not installed here" verdict and the whole `installation_repos_cache` table. Those sweeps only ever fire for the mirror's OWN App (a consumer App's installation events never reach us). Both of those answers are thus bounded primarily by their own short TTLs rather than by this flush. `workflow_job` deliveries (`in_progress`/`completed` only. `queued`/`waiting` dropped as `ignored` — after the cache flush above) record job state in the global `workflow_jobs` table (admin-only `GET /api/jobs`. Out-of-order tolerant upsert. Completed rows pruned once BOTH their `completed_at` and `updated_at` are several days past. Retention keys on the last webhook touch too, because the row is the upsert guard's only memory. A prune keyed on `completed_at` alone deleted a just-recorded old completed event (delivery replays legitimately re-send those). A late in_progress then resurrected the job as a phantom running row: the 2026-07-17 CI incident). **Operator action required**: the GitHub App must be subscribed to the `workflow_job` event for that table to fill — and to the `workflow_run` event. This is now load-bearing twice over. It is the startup-failure `workflow_runs_cache` flush above, AND the only delivery that names a run with no jobs yet (one held by a concurrency group, or a startup_failure). This is the single hole the runs-listing completeness marker's short TTL exists to bound. Without that subscription the backlog listing still answers correctly, just re-fetching every couple of minutes instead of serving from rows. **You do not have to remember this.** The dashboard's Webhooks tab reports every required subscription the App actually lacks, and what each one costs (`ghdata.RequiredWebhookEvents` diffed against `AppAuthenticator.SubscribedEvents`. See docs/dashboard/dashboard.md).

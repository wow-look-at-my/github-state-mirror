# Admin operator tooling: truth browse, grants, consistency check/reconcile

Extracted verbatim from CLAUDE.md, which keeps the one-line index entry.

**Admin truth browse, grants view + consistency check/reconcile (admin-only operator tooling)** — `GET /api/cache/data` dumps the GLOBAL truth rows (repos with visibility, open PRs, commit checks) as flattened JSON; `GET /api/cache/data?principal=<key>` instead dumps that principal's **access grants** (who can see what, each grant's source and expiry) — surfaced as the "Browse truth" / "Run consistency check" / "Reconcile" buttons on the admin Principals tab and a per-principal "Grants" button. `GET /api/cache/check[?org=<owner>]` runs the **consistency check** (`internal/sync/consistency.go` + `consistency_diff.go`): it re-fetches the source of truth from GitHub via the mirror's **GitHub App** (`AppAuthenticator`, shared with background refresh) using the owner-agnostic `GetOwnerData` + `OwnerRepoVisibilities` — so **User-account installations are checked like Organizations** (only owners with no installation are skipped, under `orgs_skipped`) — and diffs GLOBAL truth against it. Compared: repo/PR existence both ways; repo fields `default_branch_status`, `default_branch` (its mismatch entry always carries an explicit github value — `(none)` + a note when GraphQL's `defaultBranchRef` is null, e.g. an empty repo whose cached name is REST's configured default, so the entry can never lose its github side to JSON omitempty), `is_disabled`, `url`, `is_archived`, `pushed_at` (5-minute tolerance — lag = missed push webhooks = possibly stale `contents_cache`), and `visibility` — the reveal layer's security field: cached-public/GitHub-nonpublic gets its own `visibility_leak` issue + summary tally, cached `''` reports as informational `visibility_unknown`; PR fields incl. `last_commit_status` and `auto_merge_method` (fetched via `autoMergeRequest`), plus labels (100 per PR on this path). `mergeable` is deliberately not compared — the cache un-resolves it on pushes. **In-flight movement is not drift**: the report carries `check_started_at` (captured before any fetch), and a `pushed_at` mismatch whose GITHUB-side value is at/after it — or a `head_ref_oid` mismatch whose PR's GitHub-side `updated_at` is (the in-flight proof the owner-query snapshot carries) — classifies as the informational `raced_during_check` (own summary tally + "re-run to confirm" fix hint), never `field_mismatch`; strictly-before values keep the normal drift classification, and apply mode still corrects raced entries from the fetched snapshot (idempotent — only the report classification changes). An only-in-cache repo that is **archived** (the visibility twin has no `isArchived` filter) is classified expected, not drift (tallied in `repos_only_in_cache_archived`); cached-open PRs under an only-in-cache repo are swept as their own `pr only_in_cache` entries; PR-existence entries carry `served_now` (derived from the repo's live `pulls_list_cache` marker, read WITHOUT touching its LRU) and only-in-cache PR entries carry the cached title/updated_at/touched_at; every discrepancy gets a per-class `fix` hint; a failed visibility fetch becomes a per-owner report note, never a silent gap. The report carries `truth_freshness`: per owner, the NEWEST org list-sync marker any principal holds — an owner with NO marker rows at all is surfaced explicitly as state `never_synced` (never silently omitted; that omission once hid "the fleet refresher never completed a cycle"). The GET is **read-only** and compares **OPEN** PRs only; returns **503** when no App is configured. **Streaming mode** (`?stream=1`, GET and POST alike): the same route answers `application/x-ndjson` — one JSON line per checker progress event (`internal/sync/progress.go` `ProgressEvent`, phases start/owner/fetch/visibility/diffed/applied/skip/done; the per-page fetch events come from `ghclient.GetOwnerDataWithProgress` + the owner query's `totalCount`, an owner-only extra the locked org query never grows), each line flushed immediately (Cloudflare-safe), ending with `{"phase":"report",report}` carrying the exact non-stream report (or `{"phase":"error"}`); the run stays on the request context so closing the dashboard modal aborts it (apply corrections are idempotent), non-stream responses are unchanged, and the dashboard modal renders these lines as a live per-owner/per-page progress bar (`internal/api/checkstream.go`). **Apply mode** (`POST /api/cache/check?apply=true`, alias `?apply=1`; `?apply` on a GET is a 405 — `internal/sync/consistency_apply.go`): after the diff, the drift is CORRECTED from the same fetched snapshot, per owner under `AppInstallationActor(inst.ID)` with `fetchStart` captured before the fetch — (1) `SyncOrgTruth` absorbs repos + open PRs + labels + statuses and deletes stale cached-open PRs (grace-guarded); (2) `SetRepoVisibility` from the visibility map (fail-closed `''` rows and drift both directions); (3) `SetRepoDefaultBranchStatus` with GitHub's value INCLUDING NULL (never rely on the COALESCE upsert); (4) the **commit_checks stick rule**: a terminal GitHub rollup (SUCCESS/FAILURE/ERROR) contradicted by recorded rows → `ForceCheckRollup` (one tx: delete the sha's rows + `SetPRStatusByHeadSha`); an empty GitHub rollup with leftover rows or a non-NULL column → the same with NULL; PENDING/EXPECTED → no-op; per-check rows are NEVER synthesized (a fabricated completed row would be tomorrow's ghost), and the correction STICKS because the next PR webhook's `UpsertPRWithChecks` derives an empty rollup (guard skips) while COALESCE preserves the set value; (5) `SetPRAutoMergeMethod` including NULL (a stale armed flag would silently disable pr-minder's merge backstop); (6) the app-installation freshness marker is stamped. The response is the normal report plus an `applied` tally (repos/PRs absorbed, PRs deleted, visibility/statuses/default-branch/auto-merge set, check rows deleted); discrepancies always show the PRE-apply state. Known accepted race: `commit_checks` rows carry no timestamp, so a webhook landing between the fetch and the correction can lose one write (it re-appears on that check's next event).
